# Arquitetura de entrada de cada avaliador automatizado

Este documento descreve exatamente que informação cada avaliador automatizado (Checkov e LLM) recebe do plano Terraform, para deixar explícita qualquer assimetria de informação entre eles — relevante para interpretar corretamente comparações de desempenho entre os dois métodos.

## Checkov

Recebe o plano JSON completo (`terraform show -json`) e aplica as políticas customizadas (`common/checkov/rules/*.yaml`) diretamente sobre os atributos de cada `resource_change`. Em particular, o atributo `region` usado por `CKV_FINOPS_03` já vem **resolvido** pelo próprio Terraform no bloco `resource_changes[].change.after.region` — um atributo computado pelo provider AWS moderno, com o valor final concreto (ex.: `"us-east-1"`), independentemente de a região ter sido definida no código como valor literal ou via referência a uma variável (`var.aws_region`) alimentada por `.tfvars`. O Checkov não precisa resolver nenhuma referência de variável: ele lê um valor já calculado pelo `terraform plan`.

## LLM (avaliador_llm.py)

**Estado atual (pós-correção da arquitetura)**: recebe um payload otimizado (função `otimizar_plano_terraform`), construído para reduzir o tamanho do JSON enviado à API. O payload contém só um bloco, `recursos_modificados`, com `tags`, `instance_type`, `instance_class` e `region` de cada recurso modificado/criado — todos atributos já resolvidos pelo Terraform, lidos diretamente de `resource_changes[].change.after`, exatamente como o Checkov lê. Não há mais nenhum bloco de variáveis ou de configuração de provider bruta no payload, nem instrução de cruzamento manual no prompt: os dois avaliadores agora consomem exatamente o mesmo dado resolvido para decidir `CKV_FINOPS_03`.

**Estado anterior (histórico)**: até a correção, o payload enviava também `provedores` (a configuração bruta do provider, com a expressão de região tal como escrita no código — podendo ser uma referência não resolvida como `{"references": ["var.aws_region"]}`) e `variaveis_globais` (os valores reais de todas as variáveis do plano, vindos de `.tfvars`), pedindo ao LLM que cruzasse os dois manualmente. Essa era a origem da assimetria descrita abaixo.

**Assimetria identificada**: o LLM recebe explicitamente o bloco `variaveis_globais`, permitindo-lhe resolver por conta própria uma referência de variável que, no seu payload, aparece não resolvida (`provedores`). O Checkov não recebe nada equivalente a este bloco — mas também não precisa dele, pois o valor de `region` que ele consome já vem pré-resolvido pelo Terraform na estrutura do plano, por um caminho diferente (atributo computado no `resource_changes`, não na configuração declarada).

**Resultado empírico no `training_set`** (30 casos): tanto o Checkov quanto o LLM atingem Accuracy = 1,000 em `CKV_FINOPS_03` — a única das 5 regras que depende de resolução de região. Um estudo de ablação (`common/llm/ablacao_preprocessamento.md`) testou se essa paridade se mantém removendo o bloco `variaveis_globais` do payload do LLM: **não se mantém**. Sem esse bloco, a Accuracy do LLM em `CKV_FINOPS_03` cai para 0,077 (praticamente aleatório) — o modelo passa a "chutar" `FAILED` ou responder `N/A` indevidamente na maioria dos casos onde a região vem de uma variável.

Ou seja: a assimetria arquitetural não é inofensiva — ela é a razão pela qual o LLM consegue empatar com o Checkov nesta regra. O Checkov chega ao mesmo resultado (100%) por um caminho que não depende de nenhuma ajuda externa (o atributo `region` já vem resolvido pelo próprio Terraform); o LLM só chega lá porque foi deliberadamente instrumentado com o bloco de variáveis e uma instrução de como cruzá-las. Retirada essa instrumentação, a paridade desaparece.

## Implicação para o texto do TCC

A afirmação de que o LLM apresenta "rastreabilidade semântica superior" ao Checkov não é sustentada pelos dados — e a ablação mostrou que o motivo era mais interessante do que um simples empate: o Checkov resolvia a região de forma nativa e robusta (sem qualquer assistência externa), enquanto o LLM só alcançava o mesmo resultado graças a uma instrumentação de engenharia específica para este fim, perdendo essa capacidade quase inteiramente sem ela (ver `common/llm/ablacao_preprocessamento.md`). Recomenda-se remover a alegação de superioridade do texto.

Após esse achado, a arquitetura foi corrigida (ver seção anterior) para que ambos os avaliadores leiam exatamente o mesmo atributo já resolvido, de modo que os dois métodos automatizados passem a receber informação semanticamente equivalente. A narrativa correta para o TCC passa a ser: (1) uma assimetria arquitetural foi identificada; (2) um estudo de ablação quantificou seu impacto real, mostrando que ela era decisiva para o desempenho do LLM nesta regra; (3) a arquitetura foi corrigida para eliminar a assimetria; (4) a comparação final passa a ser sobre informação genuinamente equivalente. Isso demonstra um processo metodológico completo — diagnóstico seguido de correção — mais defensável do que a alegação original de superioridade do modelo.
